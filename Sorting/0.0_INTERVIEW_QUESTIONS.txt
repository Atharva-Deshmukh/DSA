--- BASICS ---------------------------------------------------------------------

Q: What is sorting? Why does an SDET care?
- Arranging elements in a defined order (asc/desc).
- Testing use: compare API responses deterministically, spot duplicates, verify UI tables/lists
  are ordered, make assertions order-independent (sort both sides before deep-equal).

Q: Why is O(n log n) the limit for comparison sorts?
- A comparison sort can only know how to sort based on "is a[i] > a[j]?". Nothing else. 
  So, it just checks how many "is a[i] > a[j]?"s
- There are n! permutations of n distinct array elements
- For each of the n elements, there is a decision tree (n! leaves -> log(n!) ~ n log n). This is purely mathematical.
- This TC can be beat by Non-comparision based algos: Counting / Radix / Bucket Sort -> O(n)

Q: Which sorts are in-place (O(1) extra space)?
- Yes: Bubble, Selection, Insertion, Quick (ignoring O(log n) recursion stack)
- No : Merge O(n), Counting O(k), Radix O(n+k), Bucket O(n).

Q: Stable vs unstable? Why care?
- Stable:
  --> equal keys keep input order. Needed for MULTI-LEVEL sort (sort by dept, then salary -> dept grouping survives).
  --> Bubble, Insertion, Merge, Counting, Radix, Tim Sort.
- Unstable: 
  --> Quick, Heap, Selection, Shell.
  --> Make any sort stable: sort (value, original_index) with index as tie-breaker.

Q: Why do languages use HYBRID sorts?
- No single algo wins everywhere. Tim Sort = Merge + Insertion (runs), used by Python sorted(),
  V8 Array.sort(). Insertion for small chunks, merge for big.

--- MERGE vs QUICK ----------------------------------------------------------------

Q: Merge Sort vs Quick Sort
            | Merge                      | Quick
  Time      | O(n log n) always          | Avg O(n log n), Worst O(n^2)
  Space     | O(n)                       | O(log n) stack
  Stable    | Yes                        | No
  Best for  | Linked lists, huge/external | Arrays, in-memory, fast in practice

Q: Why Merge Sort for linked lists?
- Needs only sequential access + O(1) splice to merge -> no extra array needed, stays stable.
- Quick Sort needs random access for pivot/partition -> poor on lists.

Q: Why Quick Sort for arrays?
- In-place, random access is O(1), better cache locality than Merge's extra array.

Q: Quick Sort worst case and how to avoid it?
- O(n^2) when pivot is always min/max (already sorted / reverse sorted input).
- Avoid: randomised pivot

Q: When prefer Insertion Sort?
- ONLINE/streaming input OR Nearly sorted data (inner loop barely runs -> O(n))

Q: When prefer Counting Sort?
- Integers in a small known range k (k ~ n)

--- JS / TS SPECIFICS (the ones that actually get asked) --------------------------

Q: What does JS Array.sort() do by default?
- Converts elements to STRINGS and compares UTF-16 code units.
  [10, 9, 1].sort() -> [1, 10, 9]   <- classic bug / interview gotcha.
- Always pass a comparator for numbers: arr.sort((a, b) => a - b).

Q: Is Array.sort() stable? Algorithm? Complexity?
- Stable - GUARANTEED since ES2019 (V8 >= 7.0 uses Tim Sort). Older engines: not guaranteed.
- ECMAScript does NOT mandate the algorithm, only stability + comparator semantics.
- O(n log n) typical.

Q: Does sort() mutate?
- Yes, in place and returns the same array. Non-mutating: arr.toSorted() (ES2023) or [...arr].sort().

Q: Sort strings / locale?
- Use a.localeCompare(b) for human order;

Q: Sort objects by multiple keys?
- (a, b) => a.dept.localeCompare(b.dept) || a.salary - b.salary   // first non-zero wins

--- TESTING ANGLE (SDET twist - expect a follow-up on EVERY coding answer) ---------

Q: How do you test a sorting function?
- Empty
- single element
- two elements
- already sorted
- reverse sorted, 
- all equal
- duplicates
- negatives / zeros

Q: Sorting + pagination - common bug?
- Sorting by a NON-UNIQUE field (createdAt) -> ties reorder between pages -> duplicates/missing rows.
- Fix/test: sort by a unique deterministic key or composite (createdAt + id); test page boundaries.

Q: Sorting in distributed systems - what to test?
- Test with composite keys (timestamp + unique id), cross-shard merge, consistency after retries.

Q: Sorting with nulls?
- Clarify first: nulls first, last, ignored, or invalid? Verify it is CONSISTENT across pages
  and asc/desc. (JS: undefined always sorts to the end, comparator is not even called for it.)


Q: Why is sorting large data expensive / when NOT to sort?
- CPU O(n log n), memory for copies, network shuffle in distributed sorts.
- Don't sort if you only need min/max (O(n)), top-k (heap), membership (hash set),
  or data is streaming (use Insertion / heap, not a full re-sort).


  T1. undefined -> ALWAYS last, comparator is never called for it

  Input                              | Call                      | Output                          | Why
  -----------------------------------|---------------------------|---------------------------------|--------------------------------------------
  [3, undefined, 1]                  | .sort()                   | [1, 3, undefined]           ✔   | engine strips undefineds, sorts the rest,
                                     |                           |                                 | appends undefineds (only 1 comparator call)
  [undefined, 2, undefined, 1]       | .sort()                   | [1, 2, undefined, undefined]    | all undefineds go to the tail, count kept
  ["b", undefined, "a"]              | .sort()                   | ["a", "b", undefined]           | same rule for strings
  [3, undefined, 1]                  | .sort((a,b) => b - a)     | [3, 1, undefined]               | even in DESC undefined stays LAST -
                                     |                           |                                 | your comparator cannot move it

  T2. null with NO comparator -> string compare ("null" sorts after digits and letters)

  Input                              | Call                      | Output                          | Why
  -----------------------------------|---------------------------|---------------------------------|--------------------------------------------
  [3, null, 1]                       | .sort()                   | [1, 3, null]                ✔   | "1" < "3" < "null"
  [10, null, 9]                      | .sort()                   | [10, 9, null]                   | "10" < "9" (string!) < "null" - two bugs
                                     |                           |                                 | in one line: numeric order AND null
  [null, "a", 1]                     | .sort()                   | [1, "a", null]                  | digits < letters < "null" in UTF-16 order
  [null, undefined, 2]               | .sort()                   | [2, null, undefined]        ✔   | "2" < "null", then undefined appended
  ["b", null, "a"]                   | .sort()                   | ["a", "b", null]            ✔   | "a" < "b" < "null"

  T3. null WITH numeric comparator -> coerces to 0 -> sorts as zero -> position FLIPS asc/desc

  Input                              | Call                      | Output                          | Why
  -----------------------------------|---------------------------|---------------------------------|--------------------------------------------
  [3, null, 1]                       | .sort((a,b) => a - b)     | [null, 1, 3]                ✔   | null -> 0, 0 < 1 -> FIRST
  [3, null, 1]                       | .sort((a,b) => b - a)     | [3, 1, null]                ✔   | desc: 0 is smallest -> LAST. Flipped = BUG
  [-1, null, 1]                      | .sort((a,b) => a - b)     | [-1, null, 1]                   | null is not "first", it is ZERO - lands in
                                     |                           |                                 | the MIDDLE when negatives exist
  [-1, null, 1]                      | .sort((a,b) => b - a)     | [1, null, -1]                   | same, reversed
  [null, null, 1]                    | .sort((a,b) => a - b)     | [null, null, 1]                 | nulls compare equal to each other (0 - 0)

  T4. null + undefined TOGETHER -> opposite ends

  Input                              | Call                      | Output                          | Why
  -----------------------------------|---------------------------|---------------------------------|--------------------------------------------
  [3, null, 1, undefined]            | .sort((a,b) => a - b)     | [null, 1, 3, undefined]     ✔   | null -> 0 -> first; undefined -> forced last
  [2, undefined, null, 1]            | .sort((a,b) => b - a)     | [2, 1, null, undefined]         | desc: null (0) last of the numbers, then
                                     |                           |                                 | undefined after it - the two "empty" values
                                     |                           |                                 | are NOT treated the same

  T5. null + string method -> TypeError (crash, not wrong order)

  Input                              | Call                                      | Output                  | Why
  -----------------------------------|-------------------------------------------|-------------------------|--------------------------------
  ["b", null, "a"]                   | .sort((a,b) => a.localeCompare(b))        | TypeError           ✔   | null.localeCompare is not a fn
  [{n:"b"},{n:null},{n:"a"}]         | .sort((a,b) => a.n.localeCompare(b.n))    | TypeError               | same on an object field
  ["b", null, "a"]                   | .sort((a,b) => (a ?? "").localeCompare(b ?? "")) | [null, "a", "b"] | guard with ?? -> "" sorts
                                     |                                           |                         | FIRST (empty string < "a")

  T6. NaN / non-numeric -> comparator inconsistent -> SILENT garbage order, no error

  Input                              | Call                                      | Output                  | Why
  -----------------------------------|-------------------------------------------|-------------------------|--------------------------------
  [3, NaN, 1]                        | .sort((a,b) => a - b)                     | [3, NaN, 1]         ✔   | a - NaN = NaN -> treated as 0
                                     |                                           |                         | ("equal") -> NOTHING moved
  [3, NaN, 1, 2, 0]                  | .sort((a,b) => a - b)                     | [3, NaN, 0, 1, 2]   ✔   | partially sorted garbage; 3 is
                                     |                                           |                         | stuck before 0
  [3, "x", 1, 2, 0]                  | .sort((a,b) => a - b)                     | unpredictable           | "x" - n = NaN -> same failure;
                                     |                                           |                         | parseInt'd API values do this
  [3, NaN, 1, 2, 0]                  | .sort((a,b) => isNaN(a) - isNaN(b) || a - b) | [0, 1, 2, 3, NaN]    | guard -> consistent -> NaN last

  T7. Object field (the real API / UI table case) - broken vs fixed
  users = [{name:"x", age:30}, {name:"y", age:null}, {name:"z", age:20}]        (output shows .age only)

  Call                                                               | Output (ages)       | Why
  -------------------------------------------------------------------|---------------------|--------------------------------------
  users.sort((a,b) => a.age - b.age)                                 | [null, 20, 30]  ✔   | T3 on a field: null -> 0 -> first
  users.sort((a,b) => b.age - a.age)                                 | [30, 20, null]      | desc: null last -> FLIPS vs asc
  users.sort((a,b) => nullsLast(a.age, b.age))                       | [20, 30, null]  ✔   | fixed asc
  users.sort((a,b) => nullsLastDesc(a.age, b.age))                   | [30, 20, null]      | fixed desc - null stays LAST

  T8. Nulls-last comparator -> consistent in asc AND desc
  
    const nullsLast     = (a, b) => (a == null) - (b == null) || a - b;   // asc
    const nullsLastDesc = (a, b) => (a == null) - (b == null) || b - a;   // desc
    const nullsFirst    = (a, b) => (b == null) - (a == null) || a - b;   // asc, nulls first
    // (a == null) is true for BOTH null and undefined. true - false = 1 -> a after b.
    // || falls through to the numeric compare only when neither side is null.

  Input                              | Call                      | Output                          | Why
  -----------------------------------|---------------------------|---------------------------------|--------------------------------------------
  [3, null, 1]                       | .sort(nullsLast)          | [1, 3, null]                ✔   | null pinned last
  [3, null, 1]                       | .sort(nullsLastDesc)      | [3, 1, null]                ✔   | STILL last in desc -> consistent
  [3, null, 1]                       | .sort(nullsFirst)         | [null, 1, 3]                    | swap the subtraction -> nulls first
  [3, null, 1, undefined]            | .sort(nullsLast)          | [1, 3, null, undefined]         | undefined still appended by the engine
                                     |                           |                                 | AFTER null - note the order null, undefined
  [-1, null, 1]                      | .sort(nullsLast)          | [-1, 1, null]                   | fixes the T3 "null in the middle" case
